# 批次边界与唤醒合并

Plico 不要求应用编写 batch 闭包。应用同步修改普通 Rust 状态，Source 的 pending 标志
合并重建请求；显式 request_rebuild 不立即声明或提交后端。下面区分通知、操作与展示状态。

## 服务通知与轮询

Source 为传给 View 的唤醒回调增加线程安全的 pending gate。同一轮询之前，任意线程的
多次通知只调用一次宿主 wake。通知不携带业务数据；数据仍由服务自己的队列持有，
合并通知不会合并、覆盖或丢弃队列里的操作。

poll_async 在调用服务 poll 之前重新打开 gate。因此轮询期间、尤其是最后一次读取之后
到达的完成结果仍可安排下一次唤醒。可能多一次空轮询，但不会因合并而漏掉完成结果。
框架不在服务没有通知的情况下新增持续轮询。

HostService::poll 应排空本次可用的完成结果，依次应用全部操作，只报告展示投影是否变化。
若队列可能无界，应由具体服务设计有界队列、轮询预算以及剩余工作自唤醒。
框架不能替服务丢弃中间命令，也不替服务提供网络消息的持久化或 exactly-once 保证。

多次轮询/重建请求可以在下一次声明前合并。静态 ServiceView 在声明时才取 snapshot；
提供 snapshot_revision 的服务可在同版本下继续复用它。
键盘回调和稳定化过程也可能需要快照，不能理解为所有输入下每显示帧只能取一次快照。

## 输入是操作边界

点击、按键、文字编辑和命令不能直接压缩成最后一个值。
原生 shell 在分发下一次输入前调用 prepare_for_event，必要时消费前一个输入并更新
几何/焦点；无障碍动作队列与显式 semantic dispatch 也遵守这一边界。

因此多个输入落在同一显示帧时，允许有多次声明和几何提交，这是为事件顺序与命中正确性
保留的刷新点。自定义 host 直接调用 FrameSource 时也需要遵守这个约定，不能先无界堆积
同一按钮的 Click 再期望布尔 clicked() 返回次数。此次未改变 clicked() 的 API。

服务状态通知则不需要逐条刷新几何。100 个进度结果可全部应用，然后只显示最终进度；
100 次“新增条目”仍必须创建全部条目。

## 声明与后端提交

一次 try_declare 最多执行八轮稳定化，消费事件或同步命令可能要求下一轮声明。
各轮失效位取并集，dirty entity journal 去重并复用存储；每轮依然保留节点最终状态。
声明稳定后才同步后端，避免为每个中间状态执行布局。命令 outbox 不按值去重。

动画继续从注入时钟统一采样。绘制阶段 motion 可绕开声明；虚拟列表滚动仍可能重新声明。
首次挂载、尺寸改变、输入刷新与动画各有自己的必要提交，不承诺一个显示帧严格只有一次布局。

## 观测与验证

Source::batch_stats() 返回累计计数；在工作负载前后取差值：

- rebuild_requests：显式 request_rebuild 调用数，不包含内部所有 pending 原因。
- wake_notifications / scheduled_wakes：收到通知和实际调用宿主 wake 的次数。
- service_polls：poll_async 调用数，包含没有变化的轮询。
- frame_samples / event_flushes：渲染采样与输入前必要刷新的次数。
- declaration_batches / declaration_passes：声明批次和稳定化轮数，包含失败尝试。
- backend_commits / layout_runs：后端同步调用数与实际布局运行数。

唤醒计数来自原子变量；并发读取时各字段不是事务一致快照。业务停止发送后可精确断言差值。
其他计数由 UI 线程维护。计数不会进入应用 checkpoint。

执行：

```sh
cargo test -p plico-desktop --test batching
```

测试覆盖 100 次通知/操作合成一次唤醒与最终快照、100 个显式重建请求合成一次声明和布局、
800 次跨线程通知合并、轮询期间的新通知不丢失、三条命令跨稳定化不重复/不丢失、
连续点击遵守输入边界。它验证调度与交付次数，不是 GPU 帧率测试。
