# ESP32-P4 最小面板实测（2026-10-23）

Waveshare ESP32-P4-WIFI6-Touch-LCD-4.3，双核 400 MHz、32 MiB PSRAM，
480×800 RGB565，三缓冲 partial 模式。ESP-IDF 5.5.5、LVGL 9.5.0，
Rust nightly-2026-10-15 + std；GUI 栈 32 KiB，位于 PSRAM。
本次是独立显示/触摸固件，没有运行 USB、SIP、网络或音频业务。

## 稳定版本的数据

使用同一次启动先初始化显示/触摸，再挂载 Plico 计数器、两个按钮和条件详情文本。
CPU 每 2 秒用 FreeRTOS task runtime 与每核 idle 时间差估算，不是瞬时峰值或功耗测量。

| 项目 | 实测 |
| --- | --- |

| Plico 静态界面 core1 占用 | 0.62–0.63% |
| 手动连续点击期间 core1 占用 | 最高观察到 1.41%（2 秒窗口） |
| core0 空闲界面占用 | 约 0.95%，包括诊断任务等 |

| 无事件 update | 平均 1 µs，50 次/秒，无重新声明 |
| 手动点击窗口内 update 最长一次 | 1,452 µs，包含事件处理、声明、同步及点击日志，不含之后的绘制/扫描输出 |

显示缓冲、GUI 任务栈、已链接静态数据和初始化资源在基线中。
小界面短时间稳定不等于已验证复杂页面或长期无泄漏。

## 功能与故障记录

- 原生 LVGL CLICKED → Rust 事件队列 → Plico 状态与声明链路通过。
- 原生对象身份复用、条件节点创建/销毁、重复同步无样式/文本写入自测返回 0。
- 增加按钮和文本几何中心断言，稳定版本通过；用户确认文字已居中。
- 修复 LVGL flex 对齐映射：单行按钮需要同时设置 main、cross 和 track 对齐。
  只设置 cross 会让整条 flex track 仍停留在顶部。
- 中途位置断言失败曾调用 abort，导致白/蓝屏与反复重启；已改成记录自测失败，
  不因诊断失败重启。最终版本自测为 0，日志正常连续运行。

## 重建与采集

```sh
python3 scripts/build-esp32p4-firmware.py
python3 scripts/flash-esp32p4.py
# 停止其他串口监视器后，在有 dialout 权限的终端运行：
espflash monitor --port /dev/serial/by-id/usb-1a86_USB_Single_Serial_5CF7197112-if00 \
  --monitor-baud 2000000 --non-interactive
```

完整固件宿主位于 `apps/lvgl-esp32p4/idf/`。构建脚本在 target 下导出固定的
Waveshare BSP 提交 dc1b2085381c9cc3a2badf8d317673cca9079c1f，
然后复用 `scripts/build-esp32p4.py` 构建 Rust 静态库并链接。
烧录脚本验证设备现有 factory app 是 0x200000/8 MiB，私有保存并校验原 app
备份后只写 app，不替换 bootloader、分区表和 NVS。
原始串口采样保存在本地忽略的 reports 下。

目前结果支持继续开发小型状态/按钮面板。接入 USB、SIP、音频后，仍需验证并发
通话时的响应、任务调度、内存峰值和长期运行；本次不能替代这些验证。

## 同日动画实验

示例增加 12 根错相正弦信号柱、往返进度条和暂停按钮。数据是演示数据。
宿主传入时间，Rust 更新普通状态，经 Plico declare_until_settled 和 adapter.sync
更新既有原生对象，LVGL 排版/绘制；没有使用 lv_anim 绕过 Plico。
这不是 Plico 通用动画 API 的验证，也没有调用新后端的 sync_delta 增量入口。

| 项目 | 实测 |
| --- | --- |
| 动画实际声明频率 | 约 24–25 次/秒 |
| 播放时 core1 占用 | 约 34–36%（2 秒采样窗口） |
| 播放时 core0 占用 | 约 5% |
| 用户暂停后 core1 占用 | 约 0.64–0.65% |
| 用户暂停后 core0 占用 | 约 0.95% |
| 播放时 update 平均时间 | 约 4.5 ms，包含约一半无更新的 timer 调用 |
| 播放时 update 最长观察值 | 约 9.6 ms，不含随后绘制 |
| 首次挂载耗时 | 16,866 µs |
| GUI 栈最小剩余 | 15,128 B |

同一次动画固件启动：挂载前 PSRAM 空闲 30,284,448 B，播放时
30,197,148 B，暂停后 30,197,080 B；相对基线增量约 **85.3 KiB**。
挂载前/播放时内部 RAM 空闲均为 370,199 B。采样期间动态内存稳定，
原生回调/对象复用/条件节点/按钮居中自测返回 0，用户确认动画流畅。
暂停后界面保留、更新声明次数降至 0，CPU 回落，说明静止页面没有持续重建。

持续改变 12 个带圆角对象的尺寸会触发大量布局与重绘；该负载的总 CPU 占用不能
单独归因于 Plico，也不能代表只改变少量状态的正式面板。适合继续开发面板，
正式版应按状态变化更新，再对通话和动画并发做资源测量。

## 与 LVGL 原生动画对照

使用 `PLICO_P4_ANIM_BENCH=1` 构建固件，同一次启动自动切换模式。
底部小标签显示模式；同样的原生对象、配色、圆角、三缓冲、正弦公式和尺寸范围。
Plico 阶段约每 2 秒声明 48–49 次，原生阶段约每 2 秒更新 50 次。
原生阶段由一个 `lv_anim` 回调批量设置 12 个高度和一个宽度，直接使用 C 的 sinf；
不运行 Rust update/声明/同步。使用自定义时间 path，避免内置 linear path 的
1024 步量化使长时间动画实际频率偏低。这测的是本例直接属性动画的成本，
不是所有 LVGL 动画或所有 Plico 应用的普遍比率。

| 模式 | core1 稳定忙碌比例 | core0 稳定忙碌比例 |
| --- | --- | --- |
| 当前 Plico 全树同步路径 | 约 35.1% | 约 4.9–5.3% |
| LVGL 原生 lv_anim，约 25 Hz | 约 19.3% | 约 4.7–5.0% |
| 同页静止 | 约 0.66% | 约 0.95% |

排除模式切换的混合采样窗口。Plico 在本例比原生多约 16 个百分点，
该核心总占用约为原生的 1.8 倍。两边都含 LVGL 布局/绘制与显示任务开销，
不能把差值全部称为 Engine 声明耗时。

原生回调计算波形并设置 13 个属性平均约 0.73 ms，不含随后布局/绘制；
Plico 活跃 update 约 9.5 ms，包含声明、样式投影和立即布局，计时范围不同，
因此不能据此声称整个原生方案快 13 倍。应以同口径的任务 CPU 为主。

当前示例调用 `adapter.sync` 全树路径；改变高度仍重设整个 native style，并在
同步末尾立即 update_layout。增量属性更新、布局合并和原生动画委托有优化空间，
尚未在此轮测量验证。原生动画设计可参考
[LVGL 9.5 文档](https://lvgl.io/docs/open/9.5/main-modules/animation.html)。

原生阶段仍保留 Plico Engine/adapter/原生树，额外只出现少量动画记录分配；
这次不能拿其内存数字代表去掉 Plico 后的纯 LVGL 固件内存。
对照自动结束后恢复 Plico 动画；重启会再次执行这轮对照。

## 共享核心 diff 的第一轮修复与分段计时

为避免把 LVGL 成本归因于 Engine，固件在声明阶段和适配阶段分别计时，每 200 次
声明输出 `PLICO-STAGE`。旧的全树同步路径上，稳定声明阶段约 0.42–0.50 ms，
适配同步约 8.8–8.9 ms。声明阶段包含示例的 13 次波形计算和 UI 构建，
不能把它全部算成 Engine 自身成本；同步阶段包含立即布局，不是纯 diff 成本。
约 25 Hz 下，整个声明阶段约占单核 1–1.25%。

共享 Engine 修复了多轮 settle 的差异合并：以前只保留早期轮次的实体 ID，
在最终 journal 补成 `LAYOUT | PAINT | SEMANTICS`，会把纯颜色更新升级为布局，
也会丢失早期轮次的 MEASURE、TRANSFORM 等精确标记。
现在用可复用的实体→标记映射逐轮合并，最后过滤已卸载实体。
同时去掉 take_frame_delta 中临时 HashSet、临时实体 Vec 和线性查重，
保留最终输出 Vec 的预分配。所有消费 FrameDelta 的后端可共享这一修复。

回归测试在旧 Engine 上复现纯 PAINT 被扩大成 LAYOUT 的错误；修复后核心
80 项测试通过。验证在隔离副本进行，model.rs 使用当时已提交版本，因为当前
工作区另一路 model.rs 编辑尚有语法错误；没有覆盖该编辑。
当时板上运行的是分段计时的基线固件；随后工作区修复并完成了下述补测。

## 核心属性补丁 + 原生 setter（2026-10-23）

按用户反馈将属性差异的计算放入共享核心：InvalidateChannels 从同一份字段
标注同时生成 Style::diff、StyleProperties 和原有工作分类；Engine 在声明变更点
计算一次，NodeChange.properties 随 FrameDelta 跨 settle 轮次合并。
主题变化标记需重新解析的颜色属性，新节点/种类变化标记全部属性。
未标注的纯状态字段不生成渲染补丁。Style.layout 内部目前仍是一个属性位。

LVGL 后端消费这些属性位，解析主题色、默认值、百分比和本机像素值后，只调用
对应 setter；最终像素值相同也不写入。只有初次绑定完整初始化样式，日常更新
不再 remove_style_all。其他后端可复用属性补丁，尚未迁移的后端仍可消费原有
Changes 分类，不自动承诺所有后端已经获得同样性能收益。

同一动画，约 25 次更新/秒，启动后 15–40 秒的 13 个 CPU 窗口：

| 项目 | 属性补丁前 | 属性补丁后 |
| --- | --- | --- |
| core1 平均忙碌比例 | 35.552% | 21.070% |
| core1 样本范围 | 35.06–36.22% | 20.66–21.56% |
| 稳定声明 + delta 收集 | 约 0.462 ms | 约 0.469 ms |
| 稳定同步阶段 | 约 6.75 ms | 约 1.027 ms |
| 界面额外 PSRAM | 约 83.4 KiB | 约 85.0 KiB |

总 CPU 相对下降约 **40.7%**，同步阶段约下降 **84.8%**。
此前同负载原生动画对照约 19.3%，属于较早固件的历史测量，未在本版重新跑。
新日志每 200 次声明约 2,400 次原生属性 setter，即每次约 12 次（13 个动画目标
中部分像素值相同会跳过）；预热后 style_resets=0。首次 200 帧的 31 次 reset
包含初始挂载及启动自测里的条件节点创建，不代表动画仍在重置样式。

挂载前 PSRAM 空闲 30,273,436 B，预热后 30,186,404 B，增加 87,032 B
