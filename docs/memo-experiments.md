# 声明成本与 memo 实验

2026-10-21 本机 release 实验。当前没有新增 memo API、依赖追踪或组件订阅系统。目的在于区分字符串构造、声明协调、解析缓存和宿主绘制的成本，再决定是否需要子树边界。

## 重现

```sh
python3 scripts/check-memo-cost.py
```

脚本先编译全部四个入口，然后顺序执行三轮，每个条件预热 16 次、采样 120 次。CSV 记录在本地 reports/memo-experiments，包含 p50/p95 和工作量；生成产物不提交。计时受系统负载、CPU 调频及条件执行顺序影响，没有 CPU 固定、随机顺序或统计置信区间，不据小幅差异推断优化效果。

- `crates/plico/examples/memo_probe.rs`：无 renderer 的真实 Engine 声明；统计分配、节点访问、文本写入，以及声明闭包内外耗时。分配计数原子操作也包含在计时内。
- `crates/plico/examples/declaration_churn.rs`：每帧全部样式变化、反转列表、插入/删除的退化检查；包含节点工作量断言。
- `crates/plico-markdown/examples/parse_cache_probe.rs`：使用真实 `Stream::show()`，比较保留解析缓存和每次重建 Stream。固定完成消息、关闭展示动画，包含富文本；不含布局。
- `crates/plico-desktop/examples/memo_backend_probe.rs`：真实后端 retained scene 编码，虚拟时钟每次前进 16ms，比较重复声明、单节点颜色变化与宿主 opacity 动画。

均不创建窗口，不含 GPU 提交、present、操作系统事件、热重载协议或 JSON 往返；不是 FPS 测试，也不代表所有真实应用。没有实现单树 memo，因此没有完成其事件/主题/布局正确性验证。

以下第 1–5 节保留优化前基线和架构结论；实际优化后的对比见第 6 节。

## 1. 稳定身份和零分配不能跳过声明

每行一个带业务 key 的 row 和两个 text，共三个节点。以下为三轮各自 p50 的范围：

| 行数 / 节点数 | 完全不变 | 每帧只改变一个文字 |
|---|---:|---:|
| 100 / 300 | 47–49 µs | 47–49 µs |
| 1000 / 3000 | 395–418 µs | 395–418 µs |
| 10000 / 30000 | 5.84–6.50 ms | 5.94–6.09 ms |

预热后以上条件分配次数均为零；不变时 text_writes 为 0，稀疏变化时为 1，但 visited 始终等于全部节点数。断言同时验证无创建/删除，没有调用模拟测量或布局。

属性 diff 实际发生在声明节点的 mutation site，而不是声明结束后另有独立的全属性 diff。闭包内部计时包含构建器、身份查找、属性比较和写入；闭包外还包含 frame 初始化、删除扫描、子节点缓冲交换和变更汇总，不能简单称为纯 diff。3 万节点时，闭包外仍约 0.5ms，意味着仅跳过函数体不足以消除所有整树成本。

## 2. 字符串优化解决分配，不消除遍历

1 万行的稳定标签：

| 文字来源 | 每帧分配次数 | 请求分配字节 | p50 范围 |
|---|---:|---:|---:|
| 预生成 String，声明时借用 | 0 | 0 | 5.84–6.50 ms |
| 每次 format! | 10000 | 540000 | 6.10–6.41 ms |
| 复用缓冲的 text! | 0 | 0 | 6.15–6.44 ms |

字节数是分配器请求量，不是常驻内存增量。三者最终文字不变，text_writes 都为 0。text! 避免临时分配但仍执行格式化，不能推断它与借用已有字符串同样便宜；这些计时范围也不足以声称固定的加速比例。

## 3. Markdown 已有计算缓存，但仍声明节点

1000 条已完成短消息，共 9000 个 UI 节点：

- 保留 Stream：每帧新增解析字节为 0，p50 为 1.80–1.86ms。
- 每次重建 Stream：每帧重新解析 179000 字节，p50 为 2.57–2.63ms，同时包含 Stream/字符串重建开销，不是单独的解析器耗时。
- 两者都声明 9000 个节点，预热后无节点创建、删除或文本写入。

这证明计算缓存已有收益，也不能代替声明范围缩小。十条消息的样本噪声较大，不能据此声称缓存更慢。真实聊天还应先限制可见消息范围；本实验故意声明全部历史，用于暴露成本。

## 4. 宿主动画确实可以跳过 show，但并不免费

后端场景为 1000 个 text 加一层 column。以下也是三轮 p50 范围：

| 条件 | CPU 时间 | 120 次采样中的 show 次数 | 每帧 sync visits | layout runs | scene builds |
|---|---:|---:|---:|---:|---:|
| 直接重复请求不变画面 | 357–373 µs | 120 | 0 | 0 | 0 |
| 每次 request_rebuild，内容不变 | 357–373 µs | 120 | 0 | 0 | 0 |
| 每帧改变一个节点颜色 | 432–456 µs | 120 | 1 | 0 | 1 |
| 长 opacity 动画的中间帧 | 265–275 µs | 0 | 1 | 0 | 1 |

opacity 使用虚拟时钟推进，采样窗口内仍在动画；不是用省略帧伪造跳过。全部条件 flatten visits 为 0。不变画面每次复用 scene；动画/颜色变化仍重新编码 scene，所以跳过 show 不意味着整帧 O(1)。

需要澄清：本节记录调度优化前的 Source::prepare_frame_at 在通常路径会执行声明，pending=false 并不是通用的声明缓存；animation_only 有专门的跳过路径。“空闲不声明”依赖外层调度不请求新帧，不能理解成 Source 每次被调用都自动跳过。这个实验也不证明外层实际每 vsync 都请求帧。后续原生 retained 路径已补充干净帧复用，见 [声明帧与保留帧](frame-scheduling.md) 和第 7 节。

## 5. 更新边界的潜在收益，不是 memo 实现

核心实验另建 100 个独立 Engine，每个保留 100 行；只执行其中一个，其他 99 个保持不动。总计仍保留 1 万行，但每次仅访问 300 节点，p50 约 38–40µs。

它说明避免执行无关区域的潜在收益很大，但不是真正的子树 memo：没有共享布局、父子约束、事件路由、选择、主题传播和场景组合，状态检查也不在计时内。不能将它与单 Engine 的结果直接当成可兑现加速倍数，或据此采用多 Engine 应用架构。

## 设计结论

- 普通数百节点区域的绝对声明成本较小，不应默认要求每个按钮或布局加 memo。
- 大树反复声明的成本真实存在；零分配和 key 无法完全解决。应优先虚拟化、合并更新、避免不必要的应用逻辑帧，并评估粗粒度更新边界。
- 宿主动画路径已经有效，应继续区分应用逻辑和表现动画；同时后端场景编码仍有独立优化空间。
- 暂不引入自动依赖图。若下一步做单树显式缓存原型，应同时验证保留子树、全树扫描成本、内部交互、祖先约束、主题、删除/重排、热重载失效及未命中开销。仅缓存闭包返回值或重放节点 Vec 不足以证明收益。
- 这些是合成实验与实际 Markdown API/后端的工作量验证；尚未直接测量 Clashie 整页或 gallery 聊天页，也没有据此决定正式 memo 语法。


## 6. 已实现的透明优化

本轮没有增加调用方状态、revision、memo 标记或依赖图；组件执行模型不变。

1. **顺序匹配提示**：先取上一帧相同 sibling 位置的候选，核对 parent/key/scope 的完整 identity；相同才直接复用，失配回退原哈希表。位置不是身份，动态列表仍以业务 key 匹配。
2. **样式校验缓存**：incoming 样式和 retained 样式逐字段相等时，复用已有校验结果，跳过重复校验、分类比较和样式赋值。变化时仍校验和计算 changes；保留非法样式的失败结果，重复提交失败帧不能绕过检查。浮点 NaN 不相等，仍会重新校验并拒绝。只增加一个内部 bool，没有额外保存一份 Style。
3. **删除扫描**：成功声明中 visited 等于存活节点数减 root 时，唯一性检查保证所有存活节点都已触达，无需再扫描找删除项。其余情况保留原扫描；创建和删除同时发生也不能绕过。
4. **合并提交扫描**：frame_declarations 把子节点缓冲提交与变更汇总合并。模拟布局路径必须先提交全部 children 再 layout，因此仍保留它需要的阶段顺序。

先保存优化前的 release 二进制，再分别比较仅第 1/3/4 项、最终全部优化。三个版本轮换顺序执行，每个条件仍是 16 次预热、120 次采样、三轮；下面取三轮 p50 的中位数。它们是局部 CPU 样本，没有统计置信区间，小幅变化不作为收益结论。

| 场景 | 优化前 | 优化后 | 耗时减少 |
|---|---:|---:|---:|
| 300 节点稳定声明 | 48.0 µs | 29.6 µs | 38% |
| 3000 节点稳定声明 | 413 µs | 250 µs | 39% |
| 30000 节点稳定声明 | 5.84 ms | 2.41 ms | 59% |
| 30000 节点仅一条文字变化 | 5.97 ms | 2.40 ms | 60% |
| 1000 条已缓存 Markdown 消息 | 1.81 ms | 1.16 ms | 36% |
| 后端不变画面重新声明和准备 | 369 µs | 311 µs | 16% |
| 后端单节点颜色变化 | 445 µs | 392 µs | 12% |
| 宿主 opacity 动画 | 272 µs | 276 µs | 无可确认改善 |

核心稳定/单文字变化条件预热后仍是零分配。组件仍然全部执行，visited 未减少；收益来自每个节点更便宜和扫描减少，不是子树跳过。宿主动画本就不执行声明，本轮几乎没有收益，符合改动范围。

额外对相同的 3000 节点输入做三轮退化检查：全部样式每帧变化为 460→448µs，不据 3% 差异声称收益；全部反转为 374→259µs；每帧插入和删除一行（各三个节点）为 376→261µs。此项优化前版本来自 /tmp 中独立复制的核心源码，并撤销本轮四项改动后编译；不修改工作区，不依赖原 Wabou。这些有限场景没有发现明显退化，不意味着所有样式/树形都已覆盖。

复现新的前后对比，可在优化前后分别保存并运行同一组实验：

```sh
# 修改代码前，保留二进制
PLICO_PROBE_SNAPSHOT_DIR=/tmp/plico-probes-before python3 scripts/check-memo-cost.py
# 修改后，脚本先编译，再交替运行前后版本
PLICO_BASELINE_BIN_DIR=/tmp/plico-probes-before python3 scripts/check-memo-cost.py
```

比较要求前后使用相同探针源码、依赖版本及编译配置。快照只保留二进制，不代替源码版本记录；原始轮换三个版本的分阶段实验是本地人工运行。

验证包括 plico、plico-markdown、plico-desktop、plico-dev 的 254 项测试（含 doctest）。新增回归覆盖 key 重排/插删、作用域区分、重复 key 拒绝后恢复、空树删除、模拟布局/外部布局以及重复非法样式的校验缓存。仍未实现或宣称 memo 的交互正确性。

## 7. 原生干净帧复用

后续调度优化将原生 retained 采样和主动快照构建分开，详见 [声明帧与保留帧](frame-scheduling.md)。复用声明不再仅限于活动动画；干净的原生采样可以直接复用 Scene。memo_backend_probe 的唯一工作负载调整是把 direct_unchanged 的预期 show 次数从 120 改为 0，其余场景和采样方式不变。

保存本节改动前的 release 二进制，与新版本交替执行三轮，取各轮 p50 的中位数：

| 场景 | 本节改动前 | 本节改动后 | 采样期 show 次数 |
|---|---:|---:|---:|
| 重复请求不变画面 | 307.7 µs | 0.75 µs | 120 → 0 |
| 显式每帧 request_rebuild，内容不变 | 308.5 µs | 314.8 µs | 120 → 120 |
| 每帧改变一个节点颜色 | 389.7 µs | 392.6 µs | 120 → 120 |
| 宿主 opacity 动画 | 273.5 µs | 271.6 µs | 0 → 0 |

这说明干净采样路径省掉了声明与后端提交；其他路径未见可确认的改善，小幅差异视作噪声。不能把重复绘制微基准的比值当作应用整体加速或 FPS 增益。原来完全空闲、不请求帧的应用不会凭空获得这些时间收益。后端 158 项测试（含 6 项新的调度回归）及严格 Clippy 通过。
