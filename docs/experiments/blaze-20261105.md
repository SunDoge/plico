# Blaze prerelease retry — 2026-11-05

Tested release: [v0.20261105.1](https://github.com/indexable-inc/blaze/releases/tag/v0.20261105.1),
`blaze 0.20261105.1 (cb18c54 2026-11-05)`, Linux x86-64. This was the newest
published prerelease at the time of the test. The downloaded archive matched its
published SHA256 manifest. Installed in an isolated directory; no project toolchain,
normal Cargo configuration or source implementation was changed for Blaze.

## Results

| Workload | Result |
| --- | --- |
| Dependency-free executable, `println!("blaze probe: {}", 1 + 2)` | Compiled, linked and ran; printed `blaze probe: 3` |
| Full Plico workspace, selecting Gallery with wgpu | Dependency loading failed before application compilation, on the `wgsl-analyzer` Git dependency |
| Extracted workspace containing unchanged `plico` and `plico-macros` source | Compilation reached Plico, then failed at proc-macro expansion |
| Same extracted workspace and lockfile, normal `cargo check --locked -p plico --lib` | Passed |

The extracted workspace removes unrelated workspace members and Git dependencies.
Its smaller manifest has a separately resolved lockfile (49 packages), so it is a
compatibility probe, not a directly comparable full-workspace performance test.
The original full snapshot also passed normal Cargo's core check.

The important compiler blocker is `proc_macro_crate`'s static `CACHE`. Blaze
reports that a proc macro leaves a heap address in this static, while its next
call executes in a fresh WASM instance. It explicitly says replaying previous
calls into a shared instance is not implemented yet. This prevents `KindClass`,
`InvalidateChannels` and `#[component]` from expanding; missing generated types
and methods are subsequent errors. There is no evidence here of a renderer or
wgpu code-generation failure: compilation did not get that far.

The full workspace separately fails with an error that the Git repository was
requested again after fetching and mounting it. Removing the local rsproxy
replacement through an isolated Cargo home avoids the equivalent registry-index
error but does not avoid the Git-source error. Even `-p plico` encounters this
unrelated Git source while loading the full workspace.

## Environment requirements discovered

- An inherited `RLIMIT_MEMLOCK` of 8 MiB prevented the daemon from registering
  io_uring buffers. Raising the limit for the testing process allowed startup.
  The operating system's io_uring setting was enabled; it was not a Rust error.
- The daemon requires block-sharing/reflink support and refuses a copy fallback.
  Its initial state on tmpfs failed while placing standard-library artifacts.
  Moving the private state onto Btrfs allowed the executable probe to run.
- The copied workspace needs its own Git root. Without one Blaze treated `/tmp`
  as the checkout and failed trying to watch inaccessible entries there.
- The pinned Rust toolchain downloaded and installed automatically, followed by
  Blaze's own standard-library sources. Installation/download time is excluded
  from any interpretation of compiler speed.

The first successful executable build reported 41.53 seconds including cold
standard-library work. The extracted core failed after 46.63 seconds. These are
observations, **not a compiler speed comparison**: neither cache state nor the
work completed is equivalent to a successful Cargo build. No incremental GUI
build-speed conclusion can be drawn.

Logs are local ignored artifacts under `reports/blaze-20261105/`. The temporary
daemon was stopped after testing. No changes to Plico's macros were made to work
around Blaze's proc-macro host limitation.
