# 动机与开发体验

## 产品方向

Plico 是 Rust GUI 框架实验。它面向需要复杂布局、持续状态、异步工作和动画的应用，同时希望像 egui 一样能嵌入游戏或编辑器宿主。应用作者使用普通函数、if、for 和短期借用构建 UI；框架内部保存节点与运行时数据。

Wabou 已有的文字、布局、绘制和平台能力是当前验证基础，不需要为了尝试新 API 重写 renderer。Plico 是新的 Rust 前端与运行时项目，不继续围绕 Solid/JavaScript 设计核心。

## 为什么使用 immediate 风格

同步消费 clicked() 后可以直接修改业务数据，不必为每个交互创建长期回调、克隆状态句柄或满足 'static 捕获要求。文字、样式和可见性可以从普通状态计算。动画的理想接口是每次声明目标值，由运行时管理已有轨迹。

布局 children 闭包仍然存在，但它们在当前调用中执行，不保存到未来。目标是减少长期捕获和生命周期负担，而不是消除一切闭包。

## 为什么内部保留

重新声明不等于重新创建。稳定身份让 widget、文字资源、焦点、动画和后台任务有连续的生命周期。声明时比较轻量属性，昂贵的文字测量与布局只在相关输入变化时失效；后端对象仅按差异更新。

这项选择会消耗 CPU：请求重绘时，view 仍重新执行，遍历、查找和比较仍有成本。接受这部分开销，是为了换取直接的控制流与状态/动画 API。不能把“后端零写入”误称为“帧零成本”。

## DX 的判断标准

链式 API 的视觉效果只是其中一项。更重要的是：增加功能要理解多少规则，编译错误是否靠近问题，复杂状态是否可预测，以及运行时问题能否定位。

相较 egui，少闭包和同步事件并非独有优势。需要验证的差异是：更完整的排版、样式、主题、动画与组件组合能力，能否仍保持这种直接感。当前没有足够证据声称整体 DX 或性能超过 egui。

需要持续减少的负担包括重复的 key、显式 changed 标记、状态恢复规则，以及内部提交时序泄露到业务代码。优先用一个真实小应用验证，而不是提前建造完整 ECS、宏语言或多后端抽象。
